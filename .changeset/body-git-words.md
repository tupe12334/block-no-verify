'block-no-verify': patch
---

Stop blocking a long one-line commit message or PR body because it has many `git` words. When a command's `git` words would go past the parse limit, and the command has no hook-skip signal, the check now runs again with the `git` words inside quoted `-m`, `--message`, `--title`, `--body` or `--notes` values of `git` or `gh` statements left unparsed, because the shell never runs that text. A hook-skip signal is any `--no-verify`-like flag, `-n` short option, `core.hooksPath` text, `alias`, hook-manager env var (`HUSKY`, `LEFTHOOK`, `OVERCOMMIT`, `SKIP=`), or quote-split `git`, `gh` or sub-command word; a command with one is still blocked with the "could not check this command" reason. The second check only runs for commands the first one blocks, so no other result changes. It also needs values that message masking accepts: one quoted part with no command substitution, in a command with no `#`, `alias`, heredoc, `$'…'` or `$"…"` quoting, or unquoted newline. Since 1.4.5, `detectGitCommand`, `hasNoVerifyFlag` and `hasHooksPathOverride` throw an `InputTooLongError` when their input is too large to check; their docs now say so. `checkCommand` blocks such input and does not throw.
